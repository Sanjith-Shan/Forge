# Forge — Rust Embedded Code Generator

## What This Project Is

A Rust CLI tool that reads a TOML config file describing an embedded hardware setup (which peripherals are connected, on which pins/buses, at what settings) and generates ready-to-compile C source files with all the initialization code, interrupt handler stubs, and a main loop skeleton.

Think of it like Prisma for embedded hardware. You describe your board, it writes your boilerplate.

## Why It Exists

When starting an embedded project, engineers write the same C initialization patterns over and over — I2C bus setup, SPI configuration, UART serial init, GPIO pin modes, interrupt handlers. The structure is always the same, only the specific addresses, pins, baud rates, and bus numbers change. This tool eliminates that repetitive work.

## Project Name

`forge` (as in forging embedded code from a blueprint). The binary should be called `forge`.

## Input Format — board.toml

The user creates a TOML file describing their board. Here is an example with every supported peripheral type:

```toml
[board]
name = "jupiter_v2"
mcu = "esp32c6"              # Informational, appears in generated comments
clock_mhz = 160              # System clock, used for baud rate calculations

[[gpio]]
pin = 13
mode = "output"              # "input", "output", "input_pullup", "input_pulldown"
label = "status_led"         # Human-readable name, becomes C identifier

[[gpio]]
pin = 4
mode = "input_pullup"
label = "user_button"
interrupt = "falling"        # Optional: "rising", "falling", "both", "none"

[[i2c]]
bus = 0
sda_pin = 21
scl_pin = 22
speed_khz = 400              # 100 (standard) or 400 (fast)
label = "sensor_bus"

[[i2c.device]]
address = 0x2C               # 7-bit I2C address
label = "potentiometer"      # Becomes part of C function names

[[i2c.device]]
address = 0x68
label = "imu"

[[spi]]
bus = 0
mosi_pin = 23
miso_pin = 19
sck_pin = 18
label = "display_bus"

[[spi.device]]
cs_pin = 5
label = "oled"
mode = 0                     # SPI mode 0-3
speed_mhz = 10

[[uart]]
index = 1                    # UART peripheral index (0, 1, 2)
tx_pin = 17
rx_pin = 16
baud = 115200
label = "debug_serial"

[[uart]]
index = 2
tx_pin = 25
rx_pin = 26
baud = 9600
label = "gps"
```

## Output Files

Given the example config above, `forge` generates the following files in the output directory:

### 1. `init.h` — Header with all initialization function declarations

```c
/**
 * Auto-generated by Forge for board: jupiter_v2
 * MCU: esp32c6 @ 160 MHz
 * DO NOT EDIT — regenerate from board.toml
 */

#ifndef FORGE_INIT_H
#define FORGE_INIT_H

#include <stdint.h>

/* GPIO */
void gpio_init_all(void);

/* I2C */
void i2c_sensor_bus_init(void);
void i2c_sensor_bus_write(uint8_t addr, uint8_t reg, uint8_t *data, uint16_t len);
void i2c_sensor_bus_read(uint8_t addr, uint8_t reg, uint8_t *data, uint16_t len);

/* SPI */
void spi_display_bus_init(void);
void spi_oled_select(void);
void spi_oled_deselect(void);
void spi_display_bus_transfer(uint8_t *tx, uint8_t *rx, uint16_t len);

/* UART */
void uart_debug_serial_init(void);
void uart_debug_serial_send(const uint8_t *data, uint16_t len);
void uart_gps_init(void);
void uart_gps_send(const uint8_t *data, uint16_t len);

/* Master init */
void board_init(void);

#endif /* FORGE_INIT_H */
```

### 2. `init.c` — Implementation of all initialization functions

Each function contains the register-level setup calls as commented pseudocode (since actual register addresses are MCU-specific, the generated code uses readable placeholder macros that a developer fills in or maps to their HAL). The structure and flow should be correct even if the exact register names are generic.

```c
#include "init.h"

void gpio_init_all(void) {
    /* Pin 13: status_led (output) */
    GPIO_SET_MODE(13, GPIO_MODE_OUTPUT);

    /* Pin 4: user_button (input, pull-up, interrupt on falling edge) */
    GPIO_SET_MODE(4, GPIO_MODE_INPUT_PULLUP);
    GPIO_ATTACH_INTERRUPT(4, GPIO_INTR_FALLING, user_button_isr);
}

void i2c_sensor_bus_init(void) {
    /* I2C bus 0: SDA=21, SCL=22, 400 kHz */
    I2C_INIT(0, 21, 22, 400000);
}

/* ... and so on for every peripheral ... */

void board_init(void) {
    gpio_init_all();
    i2c_sensor_bus_init();
    spi_display_bus_init();
    uart_debug_serial_init();
    uart_gps_init();
}
```

### 3. `handlers.h` — Interrupt handler declarations

```c
#ifndef FORGE_HANDLERS_H
#define FORGE_HANDLERS_H

/* GPIO interrupt handlers */
void user_button_isr(void);

/* UART RX handlers (if needed) */
void uart_debug_serial_rx_isr(void);
void uart_gps_rx_isr(void);

#endif /* FORGE_HANDLERS_H */
```

### 4. `handlers.c` — Interrupt handler stubs with TODO comments

```c
#include "handlers.h"

void user_button_isr(void) {
    /* TODO: Handle falling edge on pin 4 (user_button) */
}

void uart_debug_serial_rx_isr(void) {
    /* TODO: Handle incoming data on UART 1 (debug_serial) */
}

void uart_gps_rx_isr(void) {
    /* TODO: Handle incoming data on UART 2 (gps) */
}
```

### 5. `main.c` — Main loop skeleton

```c
#include "init.h"
#include "handlers.h"

int main(void) {
    board_init();

    while (1) {
        /* TODO: Main loop */
    }

    return 0;
}
```

## CLI Interface

Use `clap` for argument parsing.

```
USAGE:
    forge [OPTIONS] <CONFIG>

ARGS:
    <CONFIG>    Path to the board TOML config file

OPTIONS:
    -o, --output <DIR>     Output directory for generated files [default: ./output]
    -v, --verbose          Print detailed generation info
    --dry-run              Parse and validate config without generating files
    --check                Validate config only, exit with 0 if valid
    -h, --help             Print help
    -V, --version          Print version
```

Examples:
```bash
forge board.toml                        # Generate into ./output/
forge board.toml -o src/generated/      # Generate into custom dir
forge board.toml --check                # Validate only
forge board.toml --dry-run -v           # Parse, validate, show what would be generated
```

## Validation Rules

The parser must catch and report clear errors for:

1. **Pin conflicts** — same pin number used by two different peripherals (e.g., GPIO pin 21 AND I2C SDA on pin 21). Error message should name both peripherals claiming the pin.
2. **Invalid I2C addresses** — must be 0x00-0x7F (7-bit). Reject addresses in the reserved ranges (0x00-0x07 and 0x78-0x7F) with a warning.
3. **Duplicate labels** — no two peripherals or devices can share the same label string, since labels become C identifiers.
4. **Invalid SPI mode** — must be 0, 1, 2, or 3.
5. **Missing required fields** — every peripheral type has required fields. If `[[i2c]]` is missing `sda_pin`, that's an error.
6. **Invalid GPIO interrupt mode** — if `interrupt` is present, must be one of "rising", "falling", "both", "none".
7. **Label format** — labels must be valid C identifiers (alphanumeric + underscore, not starting with a digit).

All errors should be collected and reported together (not fail on the first one). Use a vector of error messages and print them all before exiting with a non-zero code.

### Why tokio

The code generation step should use `tokio::task::spawn` to generate each output file in parallel (init.c, init.h, handlers.c, handlers.h, main.c are all independent of each other). This is not strictly necessary for performance at this scale, but it demonstrates async Rust fluency, which the Tesla Simulation Platform role explicitly asks for ("familiarity with async Rust"). The main function should be `#[tokio::main]`.

---

## Async Pattern

```rust
#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let args = Args::parse();
    let config = config::parse(&args.config)?;
    let board = config::validate(config)?;

    if args.dry_run {
        // Print summary and exit
        return Ok(());
    }

    // Generate all files in parallel
    let output_dir = args.output.clone();
    let handles = vec![
        tokio::spawn(codegen::generate_init_header(board.clone(), output_dir.clone())),
        tokio::spawn(codegen::generate_init_source(board.clone(), output_dir.clone())),
        tokio::spawn(codegen::generate_handlers_header(board.clone(), output_dir.clone())),
        tokio::spawn(codegen::generate_handlers_source(board.clone(), output_dir.clone())),
        tokio::spawn(codegen::generate_main(board.clone(), output_dir.clone())),
    ];

    for handle in handles {
        handle.await??;
    }

    Ok(())
}
```

## Testing Strategy

### Validation Tests
For each invalid fixture TOML, assert that the validator returns the expected error(s):
- `invalid_pin_conflict.toml` — two peripherals on same pin, expect pin conflict error naming both
- `invalid_i2c_addr.toml` — address 0x80 (out of range), expect invalid address error
- `invalid_duplicate_label.toml` — two GPIOs with label "led", expect duplicate label error

### Code Generation Tests (Snapshot Tests)
For each valid fixture TOML:
1. Run the full pipeline (parse → validate → generate)
2. Compare each generated file against the expected output in `tests/fixtures/expected/`
3. Use `pretty_assertions` for readable diffs on failure

### Integration Test
One test that runs the `forge` binary as a subprocess on `examples/jupiter.toml`, checks exit code 0, and verifies all 5 output files exist.

## Quality Bar

- `cargo clippy` must pass with no warnings
- `cargo fmt` applied throughout
- All public functions and structs have doc comments
- Error messages are human-readable and actionable ("Pin 21 is claimed by both gpio 'status_led' and i2c bus 'sensor_bus' (SDA). Each pin can only be assigned to one peripheral.")
- Generated C code should be readable and well-commented, not minified

---

## What NOT to Build

- Do not build actual HAL support for any specific MCU. The generated C uses generic macro placeholders (GPIO_SET_MODE, I2C_INIT, etc.) that the developer maps to their specific HAL. This keeps the project focused and buildable in a weekend.
- Do not build a GUI or web interface. CLI only.
- Do not add support for advanced peripherals (ADC, DAC, DMA, timers, PWM). Stick to GPIO, I2C, SPI, and UART. These four cover the most common embedded boilerplate patterns and are enough to demonstrate the concept.
- Do not integrate with any build system (CMake, PlatformIO, Makefiles). Just output raw .c and .h files.
